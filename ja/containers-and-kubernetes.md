# コンテナー — セットアップ

## 必要なもの

ジョブを実行するマシン上でアクセスできる必要があるのは、`docker` または `kubectl` プログラムのみです。他には何も必要ありません。 Docker デスクトップは必須ではありません。 Linux 上の Docker Engine、Rancher Desktop、colima、および docker 互換コマンドを備えた Podman はすべて同じように機能します。アプリはシステム パス上で見つかったコマンドを実行するだけだからです。

Kubernetes も同様に機能します。 k3s、kind、minikube、EKS、GKE、AKS などのマネージド クラスターを含む、`kubectl` 経由で到達可能なクラスターがサポートされます。

## 別のデーモンまたはクラスターの使用

別の Docker デーモンにジョブを送信するには、`DOCKER_HOST` を設定するか、`docker context use` に切り替えます。別の Kubernetes クラスターを使用するには、現在のコンテキストを `kubectl config use-context` で切り替えます。アプリはコマンド ラインで既に使用されているものに従うため、アプリ内で追加の設定は必要ありません。

## ファイルがマウントされる場所

Kubernetes の場合、フォルダーは 2 つの方法のいずれかで接続されます。ローカル開発コンテキストは、ホスト フォルダーを直接マウントします。これには、`desktop`、`colima` または `orbstack` という名前のコンテキスト、`@desktop` で終わるコンテキスト、`kind-`、`minikube` または `k3d-` で始まるコンテキスト、および名前に `docker-desktop`、`docker-for-desktop` または `rancher-desktop` を含むコンテキストが含まれます。他のすべてのコンテキストは実際のクラスターとして扱われ、代わりに永続ボリューム要求を取得します。これは、実際のクラスター ノードがデスクトップ マシン上のフォルダーを認識できないためです。`ORGANIZE_FILES_K8S_VOLUME_MODE` を `pvc` または `hostpath` に設定すると、すべてのコンテキストでこの選択が上書きされます。

## Windows 上のネットワーク フォルダー

Windows 上の Docker Desktop は、`\\server\share` などのネットワーク パスを Linux コンテナーに接続できません。 Windows はフォルダーを認識しますが、コンテナーは認識しません。これを回避するには 2 つの方法があります。ローカル ディスク上のフォルダーを使用するか、代わりにアプリ ターゲットを使用してジョブを実行します。これにより、アプリ自体で作業が行われます。共有に割り当てたドライブ文字では解決しません。アプリがそれをネットワーク パスまでたどり、同じように拒否するためです。

## 既製のファイル

Linux 用コマンドライン キットの `containers` フォルダーには、すぐに使えるファイルが入っています。キット自体からイメージをビルドする Dockerfile、Compose のサンプル、Kubernetes の Job のサンプル、そして `containers/README.md` と、その隣に言語ごとの README です。

# コンテナとCLIワーカー

## スケジュールされたジョブ — Docker および Kubernetes ターゲット

メイン ウィンドウのサイドバーから **ジョブ** を開きます。既存のカードで [**新しいジョブ**] または [**編集**] をクリックします。 [**ターゲット**] ドロップダウンで、**Docker コマンド** または **Kubernetes ジョブ** を選択します。

1. **ソース** (ホスト パス) と **出力** (ホスト パス - ジョブの実行前にすでに存在している必要があります) を設定します。
2. 他のジョブと同様に、**モード**と**実行オプション**を選択します。
3. **コマンド プレビュー** パネルには、適用される正確な `docker run` コマンドまたは Kubernetes ジョブ YAML が表示されます。
4. ジョブを **保存**して**スケジュール**を設定するか、カードの**今すぐ実行**をクリックしてすぐに開始します。

アプリは、保存されたスナップショットからマウント フラグとボリューム パスを自動的に生成します。 Docker デーモンまたは「kubectl」はホスト マシン上でアクセス可能である必要があります。 **プリフライト** は、実行が開始される前に接続をチェックし、エラーがあればジョブ ログに報告します。承認フロー、ログの取得、ヘッドレス スケジュールについては、**スケジュールされたジョブ**を参照してください。

## ホスト側の端末 (PowerShell / bash / cmd)

はい。ホストの計算機で **OrganizeFiles.Cli** を PowerShell、bash、cmd のいずれかから実行します。これが端末での支持された道筋です。Avalonia のデスクトップ窓は別の画面です。CLI 一式をアプリの隣（または PATH 上）に発行するか導入し、**--source**（繰り返し可）、**--output**、**--mode** を渡します。まずは下見の実行をお勧めします。**--execute** は用意が整ってから加えてください。

## デスクトップ画面とコンテナ

コンテナーと自動化: Avalonia デスクトップ GUI は、典型的なヘッドレス Linux コンテナー内で実行することを意図していません。複数の並列ワーカーを含む 1 つ以上の分離されたジョブの場合は、OrganizeFiles.Cli コンパニオンを使用します。各コンテナーで、ドライラン プレビュー ジョブのソース フォルダーを読み取り専用でマウントします。 **--execute** を使用した実際の移動には、エンジンがソース ツリーからファイルを再配置するため、書き込み可能なソース マウントが必要です。専用の読み取り/書き込み出力ボリュームを使用し、すべての整理/修復実行 (ドライランと実行) に対して有効なストアまたは発行者の権利を確保し、**--source** (繰り返し可能)、**--output**、および **--mode** に合格します。各同時ワーカーには独自の出力ルートが必要です。 Docker または Kubernetes ジョブを実行する前に、**Output** フォルダーがホスト上に存在している必要があります (プリフライトは、見つからない宛先を拒否し、作成しません)。パスの例: containers/README.md および containers/docker-compose.sample.yml。 Jobs/JobAgent によって生成された `docker run` は、ソースを `/in1`、`/in2`、… にマウントし、`/out` に出力します。手動の単一ソースの例では、`/in` (containers/README.md を参照) を使用する場合があります。
