# 컨테이너 — 설정

## 필요한 것

작업을 실행하는 시스템에서는 `docker` 또는 `kubectl` 프로그램에만 접근할 수 있어야 합니다. 다른 것은 필요하지 않습니다. Docker Desktop은 필수 사항이 아닙니다. Linux의 Docker 엔진, Rancher Desktop, colima 및 Docker 호환 명령을 사용하는 Podman은 모두 동일한 방식으로 작동합니다. 앱이 시스템 경로에서 찾은 명령을 실행하기 때문입니다.

Kubernetes는 동일하게 작동합니다. k3s, kind, minikube 및 관리형 클러스터(예: EKS, GKE 또는 AKS)를 포함하여 `kubectl`를 통해 연결할 수 있는 모든 클러스터가 지원됩니다.

## 다른 데몬이나 클러스터 사용

작업을 다른 Docker 데몬으로 보내려면 `DOCKER_HOST`을 설정하거나 `docker context use`로 전환하세요. 다른 Kubernetes 클러스터를 사용하려면 현재 컨텍스트를 `kubectl config use-context`로 전환하세요. 앱은 명령줄에서 이미 사용하는 모든 것을 따르므로 앱 내부에 추가 설정이 필요하지 않습니다.

## 파일이 마운트되는 위치

Kubernetes의 경우 폴더는 두 가지 방법 중 하나로 연결됩니다. 로컬 개발 컨텍스트는 직접 호스트 폴더 마운트를 얻습니다. 여기에는 `desktop`, `colima` 또는 `orbstack`이라는 이름의 컨텍스트, `@desktop`으로 끝나는 컨텍스트, `kind-`, `minikube` 또는 `k3d-`로 시작하는 컨텍스트, 그리고 이름에 `docker-desktop`, `docker-for-desktop` 또는 `rancher-desktop`이 들어 있는 컨텍스트가 포함됩니다. 다른 모든 컨텍스트는 실제 클러스터로 처리되며 대신 영구 볼륨 할당을 얻습니다. 실제 클러스터 노드는 데스크톱 시스템의 폴더를 볼 수 없기 때문입니다. `ORGANIZE_FILES_K8S_VOLUME_MODE`를 `pvc` 또는 `hostpath`로 설정하면 모든 컨텍스트에서 이 선택을 덮어씁니다.

## Windows의 네트워크 폴더

Windows의 Docker Desktop은 `\\server\share`과 같은 네트워크 경로를 Linux 컨테이너에 연결할 수 없습니다. Windows에서는 폴더를 볼 수 있지만 컨테이너는 볼 수 없습니다. 이를 피하는 방법은 두 가지입니다. 로컬 디스크의 폴더를 사용하거나, 대신 앱 대상으로 작업을 실행하세요. 그러면 앱 자체에서 작업이 수행됩니다. 공유에 연결한 드라이브 문자는 도움이 되지 않습니다. 앱이 이를 네트워크 경로까지 따라가 같은 방식으로 거부하기 때문입니다.

## 미리 만들어진 파일

Linux 명령줄 키트의 `containers` 폴더에는 바로 쓸 수 있는 파일이 들어 있습니다. 키트 자체로 이미지를 빌드하는 Dockerfile, Compose 예제, Kubernetes Job 예제, 그리고 `containers/README.md`와 그 옆에 언어별 README가 있습니다.

# 컨테이너 및 CLI worker

## 예약된 작업 - Docker 및 Kubernetes 대상

기본 창 사이드바에서 **작업**을 엽니다. 기존 카드에서 **새 작업** 또는 **수정**을 클릭하세요. **대상** 드롭다운에서 **Docker 명령** 또는 **Kubernetes 작업**을 선택합니다.

1. **소스**(호스트 경로) 및 **출력**(호스트 경로 — 작업이 실행되기 전에 이미 존재해야 함)을 설정합니다.
2. 다른 작업과 마찬가지로 **모드** 및 **실행 옵션**을 선택합니다.
3. **명령 미리보기** 패널에는 적용될 정확한 'docker run' 명령 또는 Kubernetes Job YAML이 표시됩니다.
4. 작업을 **저장**하고 **일정**을 설정하거나 카드에서 **지금 실행**을 클릭하여 즉시 시작합니다.

앱은 저장된 스냅샷에서 마운트 플래그와 볼륨 경로를 자동으로 생성합니다. Docker 데몬 또는 `kubectl`은 호스트 시스템에서 연결할 수 있어야 합니다. **실행 전**은 연결을 확인하고 실행이 시작되기 전에 작업 로그에 오류를 보고합니다. 승인 흐름, 로그 검색 및 헤드리스 예약에 대해서는 **예약된 작업**을 참조하세요.

## 호스트 컴퓨터의 터미널 (PowerShell / bash / cmd)

예 — 호스트 컴퓨터에서 **OrganizeFiles.Cli** 를 PowerShell, bash, cmd 가운데 하나로 실행하십시오. 이것이 지원되는 터미널 경로입니다. Avalonia 데스크톱 창은 별개의 그래픽 화면입니다. CLI 꾸러미를 앱 옆에(또는 PATH 에) 게시하거나 설치한 다음 **--source**(여러 번 가능), **--output**, **--mode** 를 넘기십시오. 먼저 예행 실행을 권합니다. **--execute** 는 준비가 되었을 때만 붙이십시오.

## 데스크톱 화면과 컨테이너

컨테이너 및 자동화: Avalonia 데스크탑 GUI는 일반적인 헤드리스 Linux 컨테이너 내에서 실행되도록 고안되지 않았습니다. 여러 병렬 작업자를 포함하여 하나 이상의 격리된 작업의 경우 OrganizeFiles.Cli 컴패니언을 사용하세요. 각 컨테이너 마운트 소스 폴더에는 테스트 실행 미리보기 작업에 대한 읽기 전용 폴더가 있습니다. **--execute**을 사용한 실제 이동에는 엔진이 소스 트리에서 파일을 재배치하기 때문에 쓰기 가능한 소스 마운트가 필요합니다. 전용 읽기/쓰기 출력 볼륨을 사용하고, 모든 정리/복구 실행(드라이런 및 실행)에 대해 유효한 저장소 또는 게시자 권한을 확인하고, **--source**(반복 가능), **--output** 및 **--mode**를 전달합니다. 각 동시 작업자에는 자체 출력 루트가 필요합니다. Docker 또는 Kubernetes 작업이 실행되기 전에 **Output** 폴더가 호스트에 이미 존재해야 합니다(프리플라이트는 누락된 대상을 거부하고 생성하지 않습니다). 경로 예: containers/README.md 및 containers/docker-compose.sample.yml. Jobs/JobAgent 생성 `docker run`는 `/in1`, `/in2`, …에 소스를 마운트하고 `/out`에 출력합니다. 수동 단일 소스 예제에서는 `/in`(containers/README.md 참조)을 사용할 수 있습니다.
