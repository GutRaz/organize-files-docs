# Наблюдение через Prometheus и Grafana

## Что охватывают счётчики

Запланированные задания ведут небольшой набор счётчиков и датчиков Prometheus. Каждое имя начинается с `organize_files_automation_`, и весь набор публикуется как текст Prometheus. Все три хоста, которые выполняют задания, публикуют один и тот же набор: настольное приложение, служба `OrganizeFiles.JobAgent` и хост командной строки, применяемый в контейнерах.

Счётчики описывают планировщик, а не файлы. Считаются проходы, исходы заданий, одобрения, доставка webhook и уборка истории. О файлах, которые переносит задание, не считается ничего.

## Выгрузка в файл, без открытого порта

`automation-metrics.prom` записывается в папку данных автоматизации рядом с `automation-jobs.json` и обновляется после каждого наступившего прохода и при каждом считывании. Формат тот, который читает сборщик textfile из `node_exporter`, поэтому машина, где `node_exporter` уже работает, охвачена без слушающего порта, без токена и без правила брандмауэра. Файл заменяется атомарно, а символическая ссылка, оставленная на его месте, останавливает запись, вместо того чтобы быть пройденной.

## Точка считывания

Точка считывания существует только тогда, когда `ORGANIZE_FILES_METRICS_HTTP_PORT` содержит порт от 1 до 65535. Без этой переменной ничто не слушает.

| Переменная | Действие |
| -------- | ------ |
| `ORGANIZE_FILES_METRICS_HTTP_PORT` | Порт прослушивания. Если он отсутствует или вне диапазона, точки считывания нет вовсе. |
| `ORGANIZE_FILES_METRICS_HTTP_BIND` | Адрес прослушивания. По умолчанию `127.0.0.1`. Значения `0.0.0.0`, `+` и `*` означают все адреса, а любое другое возвращает к `127.0.0.1`. |
| `ORGANIZE_FILES_METRICS_BEARER_TOKEN` | Токен bearer, требуемый на `/metrics` и на `/ready`. |
| `ORGANIZE_FILES_METRICS_READY_PUBLIC` | `1` позволяет `/ready` отвечать без этого токена, ради проб кластера. Пути хоста тогда не попадают в ответ. |
| `ORGANIZE_FILES_READY_FAIL_ON_DUE_PASS_EXIT_CODES` | Разделённые запятыми коды выхода, при которых `/ready` сообщает о неготовности. Заменяет встроенный список. |
| `ORGANIZE_FILES_READY_IGNORE_LAST_DUE_EXIT` | `1` не учитывает код выхода последнего прохода, а также состояние до завершения первого прохода. |
| `ORGANIZE_FILES_READY_JSON` | `1` требует ответ JSON на `/ready` даже для вызывающего, который попросил простой текст. |

Адрес вне локальной петли отклоняется до открытия слушателя, если не задан токен bearer. Отказ пишется в поток ошибок и отправляется как событие webhook, потому что такое сочетание отдало бы счётчики всей сети.

## Обслуживаемые пути

- `/metrics` — счётчики как текст Prometheus. Запрос к `/` возвращает то же содержимое.
- `/ready` — готовность для оркестратора. Ответ равен `200`, как только папка автоматизации принимает пробную запись, файл заданий открывается, папка истории разрешается внутри корня данных, а последний наступивший проход завершился кодом выхода, который не блокирует. Иначе ответ равен `503` с короткой причиной, такой как `due_pass_not_completed` или `last_due_pass_license_failed`.
- `/health` — только признак жизни. Этот путь остаётся анонимным даже при заданном токене, потому что отвечает `ok` и ничего больше.

Коды выхода `3` при отказе лицензии, `8` при заблокированном дереве вывода, `10` при неподтверждённом удалении и `11` при конфликте притязания по умолчанию блокируют готовность. Тело ответа на `/ready` является JSON, если вызывающий не шлёт `Accept: text/plain` и не добавляет `?format=text`.

## Счётчики

| Имя | Содержимое |
| ---- | ------------- |
| `organize_files_automation_due_passes_total` | Наступившие проходы, начатые планировщиком. |
| `organize_files_automation_jobs_started_total` | Выполнения заданий, дошедшие до рабочего состояния. |
| `organize_files_automation_jobs_skipped_total` | Пропущенные задания: среда Docker или Kubernetes не готова, задание с целью в приложении на хосте без экрана, занятый корень вывода либо задание, отклонённое оркестратором. |
| `organize_files_automation_jobs_failed_total` | Выполнения заданий, закончившиеся сбоем. |
| `organize_files_automation_jobs_awaiting_approval_total` | Настоящие выполнения, отложенные до одобрения. |
| `organize_files_automation_execute_approvals_total` | Одобрения, выданные настоящему выполнению. |
| `organize_files_automation_execute_approvals_expired_total` | Одобрения, срок которых истёк до применения. |
| `organize_files_automation_claim_conflicts_total` | Случаи, когда другой хост уже держал притязание на корень вывода. |
| `organize_files_automation_runs_orphaned_total` | Выполнения, восстановленные как осиротевшие, оставленные остановившимся хостом. |
| `organize_files_automation_job_events_total` | По одному счётчику на событие, с метками `event`, `job_id`, `target` и `jobs_file`. |
| `organize_files_automation_webhook_posts_succeeded_total` | Принятые доставки webhook. |
| `organize_files_automation_webhook_posts_failed_total` | Отклонённые или недостижимые доставки webhook. |
| `organize_files_automation_webhook_dead_letter_depth` | Строки, ожидающие прямо сейчас в файле недоставленных webhook. |
| `organize_files_automation_log_retention_pruned_total` | Журналы выполнений, удалённые сроком хранения. |
| `organize_files_automation_runs_index_compacted_total` | Строки, убранные из указателя выполнений при уплотнении. |
| `organize_files_automation_last_due_pass_exit_code` | Код выхода последнего завершённого прохода. `0` означает чистый проход. |
| `organize_files_automation_last_due_pass_completed_utc` | Время Unix в секундах последнего завершённого прохода, и `0` до первого. |

## Панель и правила оповещений

Готовая панель Grafana публикуется вместе с файлами развёртывания как `grafana-organize-files-automation.json`, под заголовком **OrganizeFiles Automation**. Её десять плиток показывают наступившие проходы, начатые и сбойные задания, конфликты притязания, пропускную способность заданий за час, последний код выхода, глубину недоставленных сообщений, отказы webhook за сутки, задания в ожидании одобрения и события заданий по состояниям. Каждая плитка называет свой источник данных через подстановку `${DS_PROMETHEUS}`.

Соответствующие правила оповещений находятся в `alerts-organize-files-automation.yaml`, а `prometheus-rule-automation.yaml` служит оболочкой Kubernetes для `kube-prometheus-stack`. Последний код выхода, отличный от нуля, предупреждает через пять минут, отказ лицензии критичен через одну, а остальные правила охватывают сбойные задания, конфликты притязания, отказы webhook, залежь недоставленных сообщений и одобрения, ожидающие сутки. Оба файла проверяются при каждой сборке, поэтому имена выше идут в ногу со счётчиками.

# Вывод выполнения и показатели

## Строка состояния

В области **Вывод выполнения** отображается:

- Текущее состояние приложения и ход работы движка.
- **CPU** и два значения **памяти** только для этого процесса.
- Строки **GPU**, в Windows: доля этого процесса на каждой видеокарте, а не вся видеокарта.

Одна и та же компактная панель ресурсов повторно используется во вторичных окнах инструментов, таких как исследование файлов, запланированные задания и восстановление файлов.

## Метки памяти

- **Private bytes/commit** — частная виртуальная память, зарезервированная процессом.
- **Рабочий набор/память** — резидентная оперативная память, которую в данный момент занимает этот процесс. Он может отличаться от монитора другой операционной системы, поскольку каждая ОС и среда рабочего стола по-разному маркируют память процесса.

## Запускаем пульс JSON (необязательно)

Включите **Запись контрольного сигнала JSON** в разделе **Дополнительно/Диагностика**. Движок записывает `Organize.Files.run.json` в `Output\_OrganizeMediaLogs` (та же папка, что и файл организации возобновления по умолчанию).

- **Путь** — обновляется атомарно во время выполнения организации и восстановления.
- **Периодичность** — во время обхода источников файл переписывается на каждые 10 000 увиденных файлов, каждые 5000 совпадений и примерно каждые 15 секунд, пока обход продолжается, поэтому большое сетевое дерево, которое медленно перечисляется, всё равно показывает, что запуск жив. Во время проверки, хеширования и перемещений он переписывается после каждых 1000 файлов, не чаще раза в 5 секунд. Записи в начале и в конце по-прежнему происходят при старте и завершении запуска.
- **Ход работы** — пока число файлов ещё растёт, главная полоса показывает увиденные до сих пор файлы вместо ста процентов, до тех пор пока у этапа не станет известен итог.
- **Поля** — `schema`, `mode`, `phase` (e.g. `enumerate`, `enumerate-done`, `classify`, `validate`, `move`, `done`), `runState` (`active` / `completed` / `failed` / `cancelled`), `utc` (ISO-8601), `dryRun`, `outputRoot`, `validateMedia`, `deepVideoValidate`, `gpuDeviceCount`, `hwaccel`, дополнительно `correlationId`, вложенные счетчики `progress`.
- **Журнал** — панель вывода выполнения печатает полный путь в начале и при сохранении файла в конце. Используйте **Открыть папку журнала пульса** / **Показать JSON-файл пульса** в разделе «Дополнительно» / «Диагностика».
- **CLI** — `--heartbeat-json` на OrganizeFiles.Cli. Отмена и фатальные ошибки оболочки записывают `cancelled` / `failed` `runState`, когда они включены.
