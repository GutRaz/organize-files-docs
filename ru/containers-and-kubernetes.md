# Контейнеры — настройка

## Что требуется

На компьютере, на котором выполняется задание, должна быть доступна только программа `docker` или `kubectl`. Больше ничего не нужно. Docker Desktop не является обязательным требованием. Docker Engine в Linux, Rancher Desktop, colima и Podman с командой, совместимой с Docker, работают одинаково, потому что приложение просто запускает команду, которую находит на системном пути.

Kubernetes работает так же. Поддерживается любой кластер, доступный через `kubectl`, включая k3s, kind, minikube и управляемые кластеры, такие как EKS, GKE или AKS.

## Использование другого демона или кластера

Чтобы отправлять задания другому демону Docker, установите `DOCKER_HOST` или переключитесь с помощью `docker context use`. Чтобы использовать другой кластер Kubernetes, переключите текущий контекст с помощью `kubectl config use-context`. Приложение следует всему, что уже используется в командной строке, поэтому никаких дополнительных настроек внутри приложения не требуется.

## Куда монтируются файлы

В Kubernetes папка прикрепляется одним из двух способов. Локальные контексты разработки получают прямое монтирование папки хоста. Это охватывает контекст с именем `desktop`, `colima` или `orbstack`, контекст, имя которого заканчивается на `@desktop`, контекст, имя которого начинается с `kind-`, `minikube` или `k3d-`, и контекст, имя которого содержит `docker-desktop`, `docker-for-desktop` или `rancher-desktop`. Любой другой контекст рассматривается как реальный кластер и вместо этого получает заявку на постоянный том, поскольку реальный узел кластера не может видеть папки на настольном компьютере. Установка `ORGANIZE_FILES_K8S_VOLUME_MODE` в значение `pvc` или `hostpath` переопределяет этот выбор для каждого контекста.

## Сетевые папки в Windows

Docker Desktop в Windows не может подключить сетевой путь, например `\\server\share`, к контейнеру Linux. Windows видит папку, а контейнер нет. Есть два способа обойти это. Используйте папку на локальном диске или запустите задание с целевым объектом приложения, которое выполняет всю работу в самом приложении. Буква диска, сопоставленная с общим ресурсом, не поможет, потому что приложение прослеживает её до сетевого пути и отклоняет так же.

## Готовые файлы

Комплекты командной строки для Linux содержат готовые файлы в папке `containers`: Dockerfile, который собирает образ из самого комплекта, пример Compose, примеры Job для Kubernetes и `containers/README.md`, а рядом README для каждого языка.

# Контейнеры и воркеры CLI

## Запланированные задания — цели Docker и Kubernetes

Откройте **Задания** на боковой панели главного окна. Нажмите **Новое задание** или **Изменить** на существующей карточке. В раскрывающемся списке **Цель** выберите **Команда Docker** или **Задание Kubernetes**.

1. Установите **Источники** (пути к хостам) и **Вывод** (путь к хосту — они должны существовать до запуска задания).
2. Выберите **Режим** и **Параметры выполнения**, как и для любого другого задания.
3. На панели **Предварительный просмотр команды** отображается точная команда docker run или YAML-файл задания Kubernetes, которая будет применена.
4. **Сохраните** задание и установите **Расписание** или нажмите **Выполнить сейчас** на карточке, чтобы начать немедленно.

Приложение автоматически генерирует флаги монтирования и пути к томам из сохраненного моментального снимка. Демон Docker или kubectl должен быть доступен на хост-компьютере. **Предварительная проверка** проверяет подключение и сообщает о любых ошибках в журнале задания перед началом выполнения. Информацию о процессе утверждения, извлечении журналов и автономном планировании см. в разделе **Запланированные задания**.

## Терминал главной машины (PowerShell / bash / cmd)

Да — на главной машине запустите **OrganizeFiles.Cli** из PowerShell, bash или cmd. Это поддерживаемый путь через терминал. Окно рабочего стола Avalonia — отдельная графическая оболочка. Опубликуйте или установите набор CLI рядом с приложением (либо в PATH), затем передайте **--source** (можно повторять), **--output** и **--mode**. Лучше начать с пробного запуска. **--execute** добавляйте только когда всё готово.

## Оболочка рабочего стола и контейнеры

Контейнеры и автоматизация: графический интерфейс рабочего стола Avalonia не предназначен для работы внутри типичного автономного контейнера Linux. Для одного или нескольких изолированных заданий, включая несколько параллельных рабочих процессов, используйте компаньон OrganizeFiles.Cli: в каждом контейнере монтируйте исходные папки, доступные только для чтения для заданий пробного предварительного просмотра. Реальные перемещения с помощью **--execute** требуют монтирования исходного кода с возможностью записи, поскольку движок перемещает файлы из дерева исходного кода. Используйте выделенный выходной том для чтения/записи, обеспечьте действительные права хранения или издателя для всех запусков организации/восстановления (пробный запуск и выполнение), передайте **--source** (повторяемый), **--output** и **--mode**. Каждому параллельному рабочему процессу нужен свой собственный выходной корень. Папка **Output** должна уже существовать на хосте до запуска заданий Docker или Kubernetes (предварительная проверка отклоняет отсутствующий пункт назначения и не создает его). Примеры путей: containers/README.md и containers/docker-compose.sample.yml. Созданный Jobs/JobAgent `docker run` монтирует источники в `/in1`, `/in2`, … и выводит в `/out`. В ручных примерах с одним источником можно использовать `/in` (см. containers/README.md).
