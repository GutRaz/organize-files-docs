# คอนเทนเนอร์ — การตั้งค่า

## สิ่งที่จำเป็น

ต้องเข้าถึงได้เฉพาะโปรแกรม `docker` หรือ `kubectl` บนเครื่องที่รันงาน ไม่มีอะไรอื่นที่จำเป็น Docker Desktop ไม่ใช่ข้อกำหนด Docker Engine บน Linux, Rancher Desktop, colima และ Podman ที่มีคำสั่งที่เข้ากันได้กับ Docker ล้วนทำงานในลักษณะเดียวกัน เนื่องจากแอปเพียงเรียกใช้คำสั่งที่พบในเส้นทางของระบบ

Kubernetes ทำงานเหมือนกัน รองรับคลัสเตอร์ใดๆ ที่เข้าถึงได้ผ่าน `kubectl` รวมถึง k3s, kind, minikube และคลัสเตอร์ที่ได้รับการจัดการ เช่น EKS, GKE หรือ AKS

## การใช้ daemon หรือคลัสเตอร์อื่น

หากต้องการส่งงานไปยัง Docker daemon อื่น ให้ตั้งค่า `DOCKER_HOST` หรือสลับด้วย `docker context use` หากต้องการใช้คลัสเตอร์ Kubernetes อื่น ให้สลับบริบทปัจจุบันด้วย `kubectl config use-context` แอปจะติดตามทุกบรรทัดคำสั่งที่ใช้อยู่แล้ว ดังนั้นจึงไม่จำเป็นต้องตั้งค่าเพิ่มเติมภายในแอป

## ตำแหน่งที่ไฟล์ถูกเมาท์

สำหรับ Kubernetes โฟลเดอร์จะถูกแนบด้วยวิธีใดวิธีหนึ่งจากสองวิธี บริบทการพัฒนาท้องถิ่นได้รับการเมานต์โฟลเดอร์โฮสต์โดยตรง ซึ่งครอบคลุมบริบทที่มีชื่อว่า `desktop`, `colima` หรือ `orbstack` บริบทที่ลงท้ายด้วย `@desktop` บริบทที่ขึ้นต้นด้วย `kind-`, `minikube` หรือ `k3d-` และบริบทที่มีชื่อประกอบด้วย `docker-desktop`, `docker-for-desktop` หรือ `rancher-desktop` บริบทอื่นๆ ทั้งหมดจะถือเป็นคลัสเตอร์จริงและได้รับการอ้างสิทธิ์วอลุ่มถาวรแทน เนื่องจากโหนดคลัสเตอร์จริงไม่สามารถมองเห็นโฟลเดอร์บนเครื่องเดสก์ท็อปได้ การตั้งค่า `ORGANIZE_FILES_K8S_VOLUME_MODE` เป็น `pvc` หรือ `hostpath` จะแทนที่การเลือกดังกล่าวสำหรับทุกบริบท

## โฟลเดอร์เครือข่ายบน Windows

Docker Desktop บน Windows ไม่สามารถแนบเส้นทางเครือข่าย เช่น `\\server\share` ไปยังคอนเทนเนอร์ Linux Windows เห็นโฟลเดอร์ แต่คอนเทนเนอร์ไม่เห็น มีสองวิธีในการเลี่ยงปัญหานี้ ใช้โฟลเดอร์บนดิสก์ในเครื่อง หรือรันงานด้วยเป้าหมายแอปแทน ซึ่งจะทำงานในแอปเอง อักษรไดรฟ์ที่แมปไปยังการแชร์ไม่ช่วย เพราะแอปจะติดตามกลับไปถึงเส้นทางเครือข่ายและปฏิเสธแบบเดียวกัน

## ไฟล์สำเร็จรูป

ชุดบรรทัดคำสั่งสำหรับ Linux มีไฟล์พร้อมใช้ในโฟลเดอร์ `containers` ได้แก่ Dockerfile ที่สร้างอิมเมจจากตัวชุดเอง ตัวอย่าง Compose ตัวอย่าง Job ของ Kubernetes และ `containers/README.md` พร้อม README ของแต่ละภาษาอยู่ข้างกัน

# คอนเทนเนอร์และ worker CLI

## งานที่กำหนดเวลาไว้ - เป้าหมาย Docker และ Kubernetes

เปิด **งาน** จากแถบด้านข้างหน้าต่างหลัก คลิก **งานใหม่** หรือ **แก้ไข** บนการ์ดที่มีอยู่ ในรายการแบบเลื่อนลง **เป้าหมาย** ให้เลือก **คำสั่ง Docker** หรือ **งาน Kubernetes**

1. ตั้งค่า **แหล่งที่มา** (เส้นทางโฮสต์) และ **เอาต์พุต** (เส้นทางโฮสต์ — ต้องมีอยู่แล้วก่อนงานจะเริ่ม)
2. เลือก **โหมด** และ **ตัวเลือกการทำงาน** สำหรับงานอื่นๆ
3. แผง **แสดงตัวอย่างคำสั่ง** จะแสดงคำสั่ง `docker run` หรือ Kubernetes Job YAML ที่จะนำไปใช้
4. **บันทึก** งานและตั้งค่า **กำหนดการ** หรือคลิก **ดำเนินการทันที** บนการ์ดเพื่อเริ่มต้นทันที

แอปสร้างแฟล็กเมานต์และพาธวอลุ่มโดยอัตโนมัติจากสแน็ปช็อตที่บันทึกไว้ ต้องเข้าถึง Docker daemon หรือ `kubectl` ได้บนเครื่องโฮสต์ **Preflight** ตรวจสอบการเชื่อมต่อและรายงานข้อผิดพลาดใดๆ ในบันทึกงานก่อนเริ่มการทำงาน สำหรับขั้นตอนการอนุมัติ การดึงข้อมูลบันทึก และการจัดกำหนดการแบบไม่มีส่วนติดต่อ โปรดดู **งานที่จัดกำหนดการไว้**

## เทอร์มินัลของเครื่องแม่ (PowerShell / bash / cmd)

ได้ — บนเครื่องแม่ให้รัน **OrganizeFiles.Cli** จาก PowerShell, bash หรือ cmd นี่คือเส้นทางผ่านเทอร์มินัลที่รองรับ ส่วนหน้าต่างเดสก์ท็อป Avalonia เป็นหน้าจอกราฟิกแยกต่างหาก เผยแพร่หรือติดตั้งชุด CLI ไว้ข้างแอป (หรือใน PATH) แล้วส่ง **--source** (ใส่ซ้ำได้), **--output** และ **--mode** ควรเริ่มด้วยการรันทดลองก่อน แล้วค่อยเพิ่ม **--execute** เมื่อพร้อม

## หน้าจอเดสก์ท็อปกับคอนเทนเนอร์

คอนเทนเนอร์และระบบอัตโนมัติ: GUI เดสก์ท็อป Avalonia ไม่ได้มีไว้สำหรับรันภายในคอนเทนเนอร์ Linux ที่ไม่มีส่วนติดต่อทั่วไป สำหรับงานแยกตั้งแต่หนึ่งงานขึ้นไป รวมถึงผู้ปฏิบัติงานแบบขนานหลายราย ให้ใช้ตัวช่วย OrganizeFiles.Cli: ในแต่ละโฟลเดอร์ซอร์สการเมาท์คอนเทนเนอร์แบบอ่านอย่างเดียวสำหรับงานแสดงตัวอย่างการทดลองรันเท่านั้น การเคลื่อนไหวจริงด้วย **--execute** จำเป็นต้องมีการเมาท์ซอร์สแบบเขียนได้ เนื่องจากกลไกจะย้ายไฟล์ออกจากแผนผังซอร์ส ใช้โวลุ่มเอาต์พุตการอ่าน/เขียนเฉพาะ ตรวจสอบให้แน่ใจว่าร้านค้าหรือผู้จัดพิมพ์ให้สิทธิ์ที่ถูกต้องสำหรับการจัดระเบียบ/ซ่อมแซมทั้งหมด (ทดลองรันและดำเนินการ) ส่ง **--source** (ทำซ้ำได้) **--output** และ **--mode** ผู้ปฏิบัติงานที่ทำงานพร้อมกันแต่ละคนต้องการรูทเอาท์พุตของตัวเอง ต้องมีโฟลเดอร์ **Output** อยู่แล้วบนโฮสต์ก่อนที่งาน Docker หรือ Kubernetes จะรัน (preflight ปฏิเสธปลายทางที่ขาดหายไปและไม่สร้างมันขึ้นมา) เส้นทางตัวอย่าง: containers/README.md และ containers/docker-compose.sample.yml Jobs/JobAgent สร้าง `docker run` เมานต์แหล่งที่มาที่ `/in1`, `/in2`, … และเอาต์พุตที่ `/out` ตัวอย่างแหล่งเดียวแบบแมนนวลอาจใช้ `/in` (ดู containers/README.md)
