# ขั้นสูง / การวินิจฉัย

## จัดระเบียบจูน

ขั้นสูง / การวินิจฉัยจะแสดงตัวเลือก **OrganizeFilesEngine** โดยไม่เกะกะแผงหลัก

โหมดการจัดระเบียบสามารถปรับแต่ง dedupe, ดัชนีปลายทาง, กฎวันที่ที่ไม่ซ้ำ, เธรดการย้ายและการแจงนับ, ส่วนเสริม BFS, ไฟล์ดำเนินการต่อ และรูทพิเศษพิเศษ

การซ่อมแซมจะเก็บเฉพาะเวลาลองซ้ำของเครือข่ายและดิสก์เต็ม เลนฮาร์ดแวร์กราฟิกที่ตรวจพบสำหรับการตรวจสอบวิดีโอแบบเต็มเสริม บัฟเฟอร์การอ่านแฮช และฮาร์ตบีต JSON ฟิลด์อื่นๆ สามารถมองเห็นได้สำหรับบริบทแต่ถูกปิดใช้งาน

เมื่อต้นทางหรือเอาต์พุตถ่ายทอดสดบนพาธ NAS หรือ UNC ความขนานที่ต่ำกว่า ให้เปิดใช้งานการลองเครือข่ายอีกครั้ง ปล่อยให้ BFS เสริมเปิดไว้สำหรับแผนผัง SMB คี่ และลองใช้บัฟเฟอร์แฮช 8 MiB หากแฮชช้า

# ขั้นสูง / การวินิจฉัย — แต่ละตัวเลือก

## เกี่ยวกับบทนี้

การควบคุมเหล่านี้คือตัวเลือกของเอนจิน เดสก์ท็อป (Windows, macOS, Linux), Android, iOS และเครื่องมือบรรทัดคำสั่งอ่านค่าเดียวกัน

โหมด **จัดระเบียบ** ใช้ทุกการควบคุมด้านล่าง เว้นแต่ UI จะทำให้เป็นสีเทา **การซ่อมแซม** ใช้เฉพาะการลองใหม่ของเครือข่าย การลองใหม่เมื่อดิสก์เต็ม เลนฮาร์ดแวร์กราฟิกที่ตรวจพบ (พร้อมการตรวจสอบวิดีโอแบบเต็ม) บัฟเฟอร์การอ่านแฮช JSON ฮาร์ทบีท **ไฟล์สถานะดำเนินการต่อ** และ **เริ่มต้นใหม่ (ตัดไฟล์สถานะดำเนินการต่อ)** ช่องอื่นๆ ยังคงมองเห็นได้แต่จะถูกละเว้นระหว่างการซ่อมแซม

## แหล่งที่มาของเครือข่าย (NAS / UNC)

เมื่อแหล่งที่มาหรือเอาต์พุตอยู่บนการแชร์ SMB/CIFS, วอลุ่ม NAS หรือไดรฟ์ที่แมป ให้ตรวจสอบส่วนนี้อย่างละเอียด

- **ทำไมต้องปรับแต่ง** — จำนวนเธรดที่ทำงานบน SSD ภายในเครื่องอาจทำให้ไฟล์หยุดทำงานหรือโอเวอร์โหลดได้
- **สิ่งที่ควรลอง** — เปิดเครือข่ายอีกครั้ง ลดเธรดการย้ายและแจงนับค่าสูงสุดแบบขนานเมื่อหมดเวลา เปิดอาหารเสริม BFS ไว้ เว้นแต่จะมีการตรวจสอบจำนวนเต็มโดยไม่มีการตรวจสอบ ลองใช้บัฟเฟอร์แฮช 8 MiB เมื่อแฮชช้าผ่านเครือข่าย
- **ปิดใช้งานการรอเครือข่าย** — ล้มเหลวอย่างรวดเร็วเมื่อมีข้อผิดพลาดของเครือข่ายชั่วคราว มีความเสี่ยงกับ Wi-Fi หรือการแชร์ที่ไม่ว่าง

## โหมด Dedupe

วิธีที่กลไกตัดสินว่าไฟล์สองไฟล์ซ้ำกัน

| โหมด | มันทำอะไร | เมื่อใดควรใช้ | การแลกเปลี่ยน |
| ---- | ------------ | ----------- | --------- |
| **แฮช (SHA-256)** | อ่านและแฮชเนื้อหาทั้งหมดของไฟล์ต้นฉบับทุกไฟล์ จากนั้นจัดกลุ่มไบต์ที่เหมือนกัน | โหมดการปฏิบัติที่แข็งแกร่งที่สุด Hash (SHA-256) จำเป็นสำหรับการลบที่ต้นทาง (ไฟล์ซ้ำและไฟล์ที่มีปัญหา) | ช้าที่สุดบนต้นไม้ใหญ่หรือ NAS ไม่ควรนำเสนออัลกอริทึมเพื่อรับประกันโดยสมบูรณ์ |
| **ขนาด+เวลา+ชื่อ** | คีย์ = ขนาด, เครื่องหมายถูกเขียนครั้งสุดท้าย UTC, ชื่อตัวพิมพ์เล็ก, จากนั้นตรวจสอบ SHA-256 แบบเต็ม | โหมดความเข้ากันได้แบบอนุรักษ์นิยมสำหรับเค้าโครงโฟลเดอร์สื่อรุ่นเก่า | สามารถพลาดการเปลี่ยนชื่อซ้ำได้ ห้ามใช้กับการลบไฟล์ซ้ำหรือไฟล์ที่มีปัญหา |
| **ไม่มี** | ไม่มีการลบข้อมูลซ้ำซ้อนข้ามไฟล์ | เรียงลำดับเท่านั้น ไม่ล้างข้อมูลซ้ำ | รายการซ้ำยังคงอยู่ในแหล่งที่มา |

## ข้ามดัชนีปลายทาง

- **ปิด (ค่าเริ่มต้น)** — สแกนเอาต์พุต **ไม่ซ้ำกัน** ที่มีอยู่และจัดทำดัชนีก่อนแฮช ปลอดภัยยิ่งขึ้นเมื่อใช้โฟลเดอร์เอาต์พุตเดิมซ้ำ
- **เปิด** — ข้ามการสแกนนั้น
- **ผลประโยชน์** — เร็วขึ้นบนต้นไม้เอาต์พุตขนาดใหญ่
- **ความเสี่ยง** — เนื้อหาที่ซ้ำกันมากขึ้นสามารถเข้าไปอยู่ใน Unique ได้

## ปีต่ำสุดของโฟลเดอร์ ไม่ซ้ำ

ปีปฏิทินขั้นต่ำสำหรับโฟลเดอร์วันที่ภายใต้ **ไม่ซ้ำกัน** ในเค้าโครงสื่อ **ทำไม** — หลีกเลี่ยงการกระจายไฟล์เก่ามากไปยังโฟลเดอร์ปีคี่เมื่อข้อมูลเมตาไม่ถูกต้อง

## ย้ายเธรด

ไฟล์แบบขนานจะย้ายหลังจากจองปลายทางแล้ว

- **สูงกว่า** — เร็วกว่าบน SSD ภายในเครื่อง
- **ต่ำกว่า** — ปลอดภัยกว่าบนไดรฟ์ NAS, USB หรือ Wi-Fi

## เธรดการจำแนกและแฮช

ตัวประมวลผลแบบขนานระหว่างการสแกนต้นทางและการขจัดข้อมูลซ้ำ SHA-256

- **เธรดการจำแนก** — การค้นหาและจำแนกไฟล์ CLI: `--classify-threads <n>`.
- **เธรดแฮช** — ตัวประมวลผลแฮชเนื้อหา CLI: `--hash-threads <n>`.
- **การแทนที่** — ค่าที่กำหนดเองจะแทนที่ค่าเริ่มต้นของโปรไฟล์ (`--profile`)

## แจกแจงค่าสูงสุดแบบขนาน

ขีดจำกัดของการแสดงรายการไดเรกทอรีแบบขนานระหว่างการสแกน

- **0** = เครื่องยนต์ อัตโนมัติ
- **ต่ำกว่า** — ลดแรงกดดันต่อ SMB เมื่อหลายโฟลเดอร์แสดงรายการพร้อมกัน

## ส่วนเสริมผ่านไดเรกทอรี

- **เปิด (ค่าตั้งต้น)** — การไล่สำรวจเพิ่มอีกรอบแบบตื้นและกว้างก่อน
- **ทำไม** — เส้นทาง NAS บางแห่งหรือต้นไม้ที่ลึกมากดูเหมือนยังไม่ครบหลังการไล่สำรวจรอบแรก
- **ปิด** — เฉพาะหลังจากยืนยันแล้วว่าจำนวนไฟล์ครบถ้วนโดยไม่ต้องใช้รอบนี้
- **CLI** — `--no-bfs` ปิดการไล่สำรวจรอบนี้

## ไฟล์สถานะดำเนินการต่อ เส้นทาง UTF-8

เสริม การย้ายที่สำเร็จจะเพิ่มบรรทัด `B64|` ไว้ต่อท้าย ดังนั้นการจัดระเบียบครั้งถัดไปจึงสามารถข้ามแหล่งที่มาที่เสร็จสิ้นแล้วได้

- **ทำไม** — ทำงานระยะยาวต่อไปหลังจากหยุดหรือชน
- **เส้นทางเริ่มต้น** — เมื่อฟิลด์ว่างในขณะรันไทม์ เอ็นจิ้นจะใช้ `Output\_OrganizeMediaLogs\OrganizeFiles.resume.txt` หากไม่มีเอาต์พุต ระบบจะใช้ `sessions\<id>\resume\OrganizeFiles.resume.txt` ใต้โปรไฟล์แอป
- **Desktop UI** — รายการพาธแบบอ่านอย่างเดียวสำหรับการเลือกและคัดลอกเมาส์ เมื่อมีไฟล์สถานะการรันอยู่ที่ตำแหน่งเริ่มต้นแล้ว เส้นทางจะปรากฏขึ้นโดยอัตโนมัติ **เรียกดู** เลือกโฟลเดอร์บันทึกและต่อท้าย `OrganizeFiles.resume.txt` **ลบ** ล้างเส้นทาง เมื่อว่างเปล่า คำใบ้จะแสดงเส้นทางที่ใช้ในขณะรันไทม์

## เริ่มต้นใหม่

ตัดทอนไฟล์สถานะการรันเมื่อการเรียกใช้การจัดระเบียบ **จริง** เริ่มต้นขึ้น (การทดลองรันไม่ตัดทอน) ด้วย **บันทึกความคืบหน้าและพื้นที่ทำงาน** จะล้างสแนปชอต UI ที่บันทึกไว้เมื่อเริ่มต้นการทำงานด้วย **ทำไม** — บังคับนับใหม่แทนที่จะดำเนินการต่อในบันทึกไฟล์สถานะการรันต่อเก่า

## รูทการสแกนพิเศษพิเศษ

หนึ่งโฟลเดอร์ต่อบรรทัด: แผนผัง **ไม่ซ้ำ** พิเศษที่จะจัดทำดัชนี (เค้าโครงดั้งเดิม วอลุ่มอื่น)

- **เหตุผล** — Dedupe สามารถดูไฟล์ที่จัดระเบียบไว้ที่อื่นแล้วโดยไม่ต้องย้ายไฟล์เหล่านั้นอีก
- **Desktop UI** — รายการแบบอ่านอย่างเดียวสำหรับการคัดลอกต่อบรรทัด **เพิ่ม** ผนวกโฟลเดอร์ที่เลือก **ลบ** จะลบบรรทัดที่เลือก (เช่น ต้นไม้ `Uniques` เก่าบน NAS)

## ลองเครือข่ายอีกครั้ง (วินาที) /

จำนวนวินาทีที่จะลองอ่านเขียนผ่านเครือข่ายซ้ำเมื่อเกิดขัดข้องชั่วคราว

- **ทำไม** — เซิร์ฟเวอร์ SMB จะตัดเซสชันที่ไม่มีการใช้งาน ใช้ทั้งตอนจัดระเบียบและตอนซ่อม
- **ปิดการรอเครือข่าย** — เลิกรอ แล้วแจ้งว่าล้มเหลวแทน

## ลองดิสก์เต็มอีกครั้ง (วินาที) /

ปิดใช้งานการรอดิสก์เต็ม รูปแบบเดียวกันเมื่อโวลุ่มเอาต์พุตหมด **ทำไม** — ถึงเวลาที่จะเพิ่มพื้นที่ว่างในดิสก์ระหว่างการรันระยะยาว

## ช่องทางของการ์ดจอ

ใช้ได้เฉพาะเมื่อ **การตรวจวิดีโอแบบเต็ม** ที่มีมาในตัวเปิดอยู่ และ **ใช้การ์ดจอที่ตรวจพบ** เปิดอยู่ด้วย ค่าที่มากกว่า **0** กำหนดจำนวนช่องทางที่ชัดเจนสำหรับการตรวจแบบขนานข้ามผู้ผลิตที่ตรวจพบ (NVIDIA, AMD, Intel, Apple, อุปกรณ์พกพา) ส่วน **0** หมายถึงให้หาจำนวนช่องทางเอง ไม่ได้หมายถึงใช้แต่หน่วยประมวลผล หากต้องการสุ่มตรวจบนหน่วยประมวลผลอย่างเดียว ให้เลือก **เฉพาะ CPU** ในรายการการ์ดจอ ป้ายกำกับช่องทางเป็นการวางแผนตรวจสายบิตบนหน่วยประมวลผล ไม่ได้เรียกใช้การถอดรหัสวิดีโอด้วยฮาร์ดแวร์ของระบบ

- **ค่าตั้งล่วงหน้าบนบรรทัดคำสั่ง** — เมื่อการตรวจวิดีโอแบบเต็มทำงาน `--hwaccel <value>` จะเลือกค่าตั้งล่วงหน้าของช่องทางตรวจ (`cpu`, `auto`, `cuda`, `qsv`, `d3d11va`, `dxva2`, `vaapi`, `apple`, `mobile`)

## บัฟเฟอร์การอ่านแฮช

บัฟเฟอร์การอ่านต่อพนักงานขณะแฮช (512 KiB, 1 MiB, 8 MiB) **ทำไม** — บัฟเฟอร์ที่ใหญ่ขึ้นช่วยเมื่อ NAS หรือการแชร์ที่มีเวลาแฝงสูงตอบช้า

## บันทึกบันทึกการเลิกทำ

บันทึก JSONL เสริมของการย้ายไฟล์ใต้รากเอาต์พุตของการทำงานนี้

- **เพื่ออะไร** — รองรับการเลิกทำผ่าน CLI หลังการจัดระเบียบจริง
- **การเก็บถาวร** — การเก็บถาวรหลังจัดระเบียบจะปิดอยู่ขณะที่บันทึกทำงาน
- **CLI** — `--record-undo-journal` (เหมือนกล่องกาเครื่องหมายในหน้าต่างหลัก)

## เขียน run heartbeat JSON

เขียนไฟล์ทางเลือก `Organize.Files.run.json` ไว้ใต้ `Output\_OrganizeMediaLogs`

- **ทำไม** — เครื่องมือภายนอกสามารถอ่านตัวนับที่กำลังทำงาน (สำรวจแล้ว วางแผนแล้ว เสร็จแล้ว) ระหว่างการจัดระเบียบหรือการซ่อม
- **ช่วงเวลาการเขียน** — ทุก 10,000 ไฟล์ที่พบ ทุก 5,000 รายการที่ตรงกัน และราวทุก 15 วินาทีระหว่างการสำรวจแหล่งที่มา หลังทุก 1,000 ไฟล์และไม่ถี่กว่าทุก 5 วินาทีระหว่างการตรวจสอบ การแฮช และการย้าย และในทุกขั้นตอนสำคัญ
