# Спостереження через Prometheus і Grafana

## Що охоплюють лічильники

Заплановані завдання ведуть невеликий набір лічильників і давачів Prometheus. Кожна назва починається з `organize_files_automation_`, і весь набір публікується як текст Prometheus. Усі три хости, що виконують завдання, публікують той самий набір: настільний застосунок, служба `OrganizeFiles.JobAgent` і хост командного рядка, який працює в контейнерах.

Лічильники описують планувальник, а не файли. Рахуються проходи, наслідки завдань, схвалення, доставка webhook і прибирання історії. Про файли, які переносить завдання, не рахується нічого.

## Вивантаження у файл, без відкритого порту

`automation-metrics.prom` записується в теку даних автоматизації поряд із `automation-jobs.json` і оновлюється після кожного належного проходу та при кожному зчитуванні. Формат той, який читає збирач textfile із `node_exporter`, тож машина, де `node_exporter` уже працює, охоплена без порту на прослуховуванні, без токена і без правила брандмауера. Файл замінюється атомарно, а символічне посилання, залишене на його місці, зупиняє запис, замість того щоб бути пройденим.

## Точка зчитування

Точка зчитування існує лише тоді, коли `ORGANIZE_FILES_METRICS_HTTP_PORT` містить порт від 1 до 65535. Без цієї змінної ніщо не слухає.

| Змінна | Дія |
| -------- | ------ |
| `ORGANIZE_FILES_METRICS_HTTP_PORT` | Порт прослуховування. Якщо його немає або він поза діапазоном, точки зчитування немає взагалі. |
| `ORGANIZE_FILES_METRICS_HTTP_BIND` | Адреса прослуховування. Усталено `127.0.0.1`. Значення `0.0.0.0`, `+` і `*` означають усі адреси, а будь-яке інше повертає до `127.0.0.1`. |
| `ORGANIZE_FILES_METRICS_BEARER_TOKEN` | Токен bearer, потрібний на `/metrics` і на `/ready`. |
| `ORGANIZE_FILES_METRICS_READY_PUBLIC` | `1` дозволяє `/ready` відповідати без того токена, задля проб кластера. Шляхи хоста тоді не потрапляють у відповідь. |
| `ORGANIZE_FILES_READY_FAIL_ON_DUE_PASS_EXIT_CODES` | Розділені комами коди виходу, за яких `/ready` звітує про неготовність. Заміняє вбудований перелік. |
| `ORGANIZE_FILES_READY_IGNORE_LAST_DUE_EXIT` | `1` не зважає на код виходу останнього проходу, а також на стан до завершення першого проходу. |
| `ORGANIZE_FILES_READY_JSON` | `1` вимагає відповідь JSON на `/ready` навіть для викликача, який попросив звичайний текст. |

Адресу поза локальною петлею відхиляють ще до відкриття слухача, якщо не задано токен bearer. Відмова пишеться в потік помилок і надсилається як подія webhook, бо таке поєднання віддало б лічильники всій мережі.

## Обслуговувані шляхи

- `/metrics` — лічильники як текст Prometheus. Запит до `/` повертає той самий вміст.
- `/ready` — готовність для оркестратора. Відповідь дорівнює `200`, щойно тека автоматизації приймає пробний запис, файл завдань відкривається, тека історії розв'язується всередині кореня даних, а останній належний прохід завершився кодом виходу, який не блокує. Інакше відповідь дорівнює `503` із короткою причиною, як-от `due_pass_not_completed` або `last_due_pass_license_failed`.
- `/health` — лише ознака життя. Цей шлях лишається анонімним навіть при заданому токені, бо відповідає `ok` і нічого більше.

Коди виходу `3` при відмові ліцензії, `8` при заблокованому дереві виводу, `10` при непідтвердженому вилученні та `11` при суперечці за право усталено блокують готовність. Тіло відповіді на `/ready` є JSON, якщо викликач не надсилає `Accept: text/plain` і не додає `?format=text`.

## Лічильники

| Назва | Вміст |
| ---- | ------------- |
| `organize_files_automation_due_passes_total` | Належні проходи, розпочаті планувальником. |
| `organize_files_automation_jobs_started_total` | Виконання завдань, що дійшли до робочого стану. |
| `organize_files_automation_jobs_skipped_total` | Пропущені завдання: середовище Docker чи Kubernetes не готове, завдання з ціллю в застосунку на хості без екрана, зайнятий корінь виводу або завдання, відхилене оркестратором. |
| `organize_files_automation_jobs_failed_total` | Виконання завдань, що скінчилися невдачею. |
| `organize_files_automation_jobs_awaiting_approval_total` | Справжні виконання, відкладені до схвалення. |
| `organize_files_automation_execute_approvals_total` | Схвалення, надані справжньому виконанню. |
| `organize_files_automation_execute_approvals_expired_total` | Схвалення, строк яких минув до вжитку. |
| `organize_files_automation_claim_conflicts_total` | Випадки, коли інший хост уже тримав право на корінь виводу. |
| `organize_files_automation_runs_orphaned_total` | Виконання, відновлені як осиротілі, залишені хостом, що спинився. |
| `organize_files_automation_job_events_total` | По одному лічильнику на подію, з мітками `event`, `job_id`, `target` і `jobs_file`. |
| `organize_files_automation_webhook_posts_succeeded_total` | Прийняті доставки webhook. |
| `organize_files_automation_webhook_posts_failed_total` | Відхилені або недосяжні доставки webhook. |
| `organize_files_automation_webhook_dead_letter_depth` | Рядки, що чекають просто зараз у файлі недоставлених webhook. |
| `organize_files_automation_log_retention_pruned_total` | Журнали виконань, вилучені строком зберігання. |
| `organize_files_automation_runs_index_compacted_total` | Рядки, забрані з покажчика виконань під час ущільнення. |
| `organize_files_automation_last_due_pass_exit_code` | Код виходу останнього завершеного проходу. `0` означає чистий прохід. |
| `organize_files_automation_last_due_pass_completed_utc` | Час Unix у секундах останнього завершеного проходу, і `0` до першого. |

## Панель і правила сповіщень

Готова панель Grafana публікується разом із файлами розгортання як `grafana-organize-files-automation.json`, під заголовком **OrganizeFiles Automation**. Її десять плиток показують належні проходи, розпочаті та невдалі завдання, суперечки за право, пропускну здатність завдань за годину, останній код виходу, глибину недоставлених повідомлень, відмови webhook за добу, завдання в очікуванні схвалення та події завдань за станами. Кожна плитка називає своє джерело даних через підстановку `${DS_PROMETHEUS}`.

Відповідні правила сповіщень лежать у `alerts-organize-files-automation.yaml`, а `prometheus-rule-automation.yaml` править за оболонку Kubernetes для `kube-prometheus-stack`. Останній код виходу, відмінний від нуля, попереджає через п'ять хвилин, відмова ліцензії критична через одну, а решта правил охоплює невдалі завдання, суперечки за право, відмови webhook, залежі недоставлених повідомлень і схвалення, що чекають добу. Обидва файли перевіряються при кожному складанні, тому назви вище тримають крок із лічильниками.

# Вивід виконання та показники

## Рядок стану

Область **Вивід виконання** показує:

- Поточний стан програми та перебіг роботи механізму.
- **CPU** і два значення **пам’яті** лише для цього процесу.
- Рядки **GPU**, у Windows: частка цього процесу на кожній відеокарті, а не вся відеокарта.

Та сама компактна панель ресурсів повторно використовується у вторинних вікнах інструментів, таких як дослідження файлів, заплановані завдання та відновлення файлів.

## Мітки пам'яті

- **Private bytes / commit** — приватна віртуальна пам'ять, зарезервована процесом.
- **Робочий набір/пам'ять** — резидентна оперативна пам'ять, яка зараз утримується цим процесом. Він може відрізнятися від іншого монітора операційної системи, оскільки кожна мітка ОС і робочого середовища обробляє пам’ять по-різному.

## Запустіть Heartbeat JSON (необов'язково)

Увімкніть **Записати, запустити серцебиття JSON** у розділі **Додатково / Діагностика**. Механізм записує `Organize.Files.run.json` у `Output\_OrganizeMediaLogs` (та сама папка, що й файл відновлення організації за замовчуванням).

- **Шлях** — оновлюється атомарно під час упорядкування та відновлення.
- **Проміжки запису** — під час обходу джерел файл переписується на кожні 10 000 побачених файлів, кожні 5000 збігів і приблизно кожні 15 секунд, доки обхід триває, тож велике мережеве дерево, яке повільно перелічується, однаково показує, що запуск живий. Під час перевірки, гешування та переміщень він переписується після кожних 1000 файлів, не частіше ніж раз на 5 секунд. Записи на початку та в кінці, як і раніше, відбуваються, коли запуск починається і завершується.
- **Поступ** — доки кількість файлів ще зростає, головна смуга показує побачені досі файли замість ста відсотків, аж доки етап не дізнається свій підсумок.
- **Поля** — `schema`, `mode`, `phase` (e.g. `enumerate`, `enumerate-done`, `classify`, `validate`, `move`, `done`), `runState` (`active` / `completed` / `failed` / `cancelled`), `utc` (ISO-8601), `dryRun`, `outputRoot`, `validateMedia`, `deepVideoValidate`, `gpuDeviceCount`, `hwaccel`, необов'язковий `correlationId`, вкладені лічильники `progress`.
- **Журнал** — панель виводу запуску друкує повний шлях на початку та під час збереження файлу в кінці. Використовуйте **Відкрити папку журналу серцебиття** / **Показати файл JSON серцебиття** у розділі Додатково / Діагностика.
- **CLI** — `--heartbeat-json` на OrganizeFiles.Cli. Скасування та фатальні помилки оболонки записують `cancelled` / `failed` `runState`, коли ввімкнено.
