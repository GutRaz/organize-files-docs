# Контейнери — налаштування

## Що потрібно

Тільки програма `docker` або `kubectl` має бути доступною на машині, яка виконує завдання. Більше нічого не потрібно. Docker Desktop не є обов’язковою умовою. Docker Engine у Linux, Rancher Desktop, colima та Podman із командою, сумісною з Docker, працюють однаково, оскільки програма просто виконує команду, яку знаходить у системному шляху.

Kubernetes працює так само. Підтримується будь-який кластер, доступний через `kubectl`, включаючи k3s, kind, minikube та керовані кластери, такі як EKS, GKE або AKS.

## Використання іншого демона або кластера

Щоб надсилати завдання іншому демону Docker, установіть `DOCKER_HOST` або переключіться на `docker context use`. Щоб використовувати інший кластер Kubernetes, змініть поточний контекст за допомогою `kubectl config use-context`. Додаток слідує тим, що вже використовує командний рядок, тому додаткові налаштування всередині програми не потрібні.

## Де монтуються файли

Для Kubernetes папка приєднується одним із двох способів. Контексти локальної розробки отримують пряме монтування папки хоста. Це охоплює контекст із назвою `desktop`, `colima` або `orbstack`, контекст, назва якого закінчується на `@desktop`, контекст, назва якого починається з `kind-`, `minikube` або `k3d-`, і контекст, назва якого містить `docker-desktop`, `docker-for-desktop` або `rancher-desktop`. Будь-який інший контекст розглядається як реальний кластер і натомість отримує запит на постійний том, оскільки справжній вузол кластера не може бачити папки на настільному комп’ютері. Встановлення `ORGANIZE_FILES_K8S_VOLUME_MODE` на `pvc` або `hostpath` перевизначає цей вибір для кожного контексту.

## Мережеві папки в Windows

Docker Desktop у Windows не може прикріпити мережевий шлях, наприклад `\\server\share`, до контейнера Linux. Windows бачить папку, але не бачить контейнер. Є два способи обійти це. Використовуйте папку на локальному диску або натомість запустіть завдання з цільовою програмою, яка виконує роботу в самій програмі. Літера диска, зіставлена зі спільною папкою, не допоможе, бо програма простежує її до мережевого шляху й відхиляє так само.

## Готові файли

Комплекти командного рядка для Linux містять готові файли в папці `containers`: Dockerfile, який збирає образ із самого комплекту, приклад Compose, приклади Job для Kubernetes і `containers/README.md`, а поруч README для кожної мови.

# Контейнери та воркери CLI

## Заплановані завдання — цілі Docker і Kubernetes

Відкрийте **Завдання** з бічної панелі головного вікна. Натисніть **Нове завдання** або **Редагувати** на наявній картці. У спадному списку **Ціль** виберіть **Команда Docker** або **Завдання Kubernetes**.

1. Установіть **Джерела** (шляхи до хостів) і **Вивід** (шлях до хостів — він уже повинен існувати до запуску завдання).
2. Виберіть **Режим** і **Параметри виконання**, як і для будь-якого іншого завдання.
3. Панель **Попередній перегляд команди** показує точну команду `docker run` або Kubernetes Job YAML, які будуть застосовані.
4. **Збережіть** завдання та встановіть **Розклад** або натисніть **Запустити зараз** на картці, щоб розпочати негайно.

Програма автоматично генерує прапорці монтування та шляхи томів із збереженого знімка. Демон Docker або `kubectl` має бути доступним на хост-машині. **Preflight** перевіряє з’єднання та повідомляє про будь-які помилки в журналі завдань перед початком виконання. Щоб отримати відомості про процес затвердження, отримання журналу та headless планування, див. **Заплановані завдання**.

## Термінал головної машини (PowerShell / bash / cmd)

Так — на головній машині запустіть **OrganizeFiles.Cli** з PowerShell, bash або cmd. Це підтримуваний шлях через термінал. Вікно робочого столу Avalonia — окрема графічна оболонка. Опублікуйте або встановіть набір CLI поряд із застосунком (чи в PATH), а тоді передайте **--source** (можна повторювати), **--output** і **--mode**. Ліпше почати з пробного запуску. **--execute** додавайте лише тоді, коли все готове.

## Оболонка робочого столу та контейнери

Контейнери та автоматизація: графічний інтерфейс робочого столу Avalonia не призначений для роботи в типовому headless контейнері Linux. Для одного чи кількох ізольованих завдань, у тому числі кількох паралельних робітників, використовуйте компаньйон OrganizeFiles.Cli: у кожному контейнері монтуйте вихідні папки лише для читання для завдань попереднього перегляду. Справжні переміщення за допомогою **--execute** вимагають монтування джерела з можливістю запису, оскільки механізм переміщує файли з дерева вихідних кодів. Використовуйте спеціальний вихідний том для читання/запису, забезпечте дійсний доступ до магазину або видавця для всіх запусків організації/відновлення (пробний запуск і виконання), пройдіть **--source** (повторюване), **--output** і **--mode**. Для кожного паралельного робочого елемента потрібен власний вихідний корінь. Папка **Output** має вже існувати на хості перед запуском завдань Docker або Kubernetes (переддрукова перевірка відхиляє відсутній пункт призначення та не створює його). Приклади шляхів: containers/README.md та containers/docker-compose.sample.yml. Jobs/JobAgent, створений `docker run`, монтує джерела на `/in1`, `/in2`, … і виводить на `/out`. Приклади з одного джерела вручну можуть використовувати `/in` (див. containers/README.md).
